## Исследование устойчивости двухуровневого управления ресурсами микросервисов при переменной нагрузке

**Цель работы** — проверить, что происходит с задержкой запросов и CPU-лимитами микросервисов при резких изменениях нагрузки. Для этого планируется собрать стенд и сравнить обычное выделение ресурсов с двухуровневым контроллером.

## 1. Проблема

Один пользовательский запрос может пройти через несколько сервисов. При этом CPU выделяется каждому из них отдельно. Контроллер видит метрики с задержкой и меняет лимиты не непрерывно, а через определённые интервалы. При скачке нагрузки он может среагировать поздно или начать менять лимиты туда-сюда. В работе предполагается измерить этот эффект и сопоставить его с экономией CPU.

В Autothrottle предложено двухуровневое управление: верхний уровень переводит сквозную цель по задержке в целевые показатели сервисов, нижний управляет ресурсами сервисов. Galileo показывает важность устойчивости к изменениям среды. Статья об HPA даёт формальную постановку устойчивости контура, но анализирует горизонтальное масштабирование числа pod, а не CPU-лимиты Autothrottle. Поэтому прямое сравнение их численных результатов некорректно.

## 2. Идея

Планируется собрать приложение из 3–5 связанных сервисов и сравнить постоянные CPU-лимиты с двухуровневым управлением. Для обоих вариантов будет использована одна и та же ступенчатая, импульсная и волнообразная нагрузка. Измеряются P95/P99 задержки (95-й и 99-й перцентили), нарушения SLO, выделенный CPU и частота изменений лимитов. Если исходный код Autothrottle не удастся перенести на стенд, будет реализован упрощённый вариант с отдельным описанием отличий от статьи.

## 3. Анализ ключевых работ

**Autothrottle** — Wang et al., NSDI 2024. Двухуровневый контроллер связывает задержку приложения с целями по CPU throttling отдельных сервисов. Проверен на трёх микросервисных приложениях и производственных трассах.
*Значение для работы:* основной метод и ближайшая база для воспроизведения. Отдельно нужно изучить период обновления, параметры контроллеров и доступность артефакта.
https://www.usenix.org/conference/nsdi24/presentation/wang-zibo

**Towards Performance Robustness for Microservices** — Saxena et al., NSDI 2026. Galileo вводит оценки устойчивости хвостовой задержки к возмущениям и использует их для выбора действий контроллера.
*Значение для работы:* помогает поставить вопрос об устойчивости к всплескам нагрузки и конкуренции за ресурсы. Полное воспроизведение модели выходит за рамки НИР.
https://www.usenix.org/conference/nsdi26/presentation/saxena

**On the Stability of the Kubernetes Horizontal Autoscaler Control Loop** — Serracanta et al., IEEE Access 2025. Модель HPA как контура обратной связи; численный анализ и реальный стенд для одного сервиса и графа сервисов.
*Значение для работы:* формальная модель устойчивости. HPA меняет число реплик, поэтому результаты нельзя напрямую переносить на управление CPU-лимитами.
https://doi.org/10.1109/ACCESS.2025.3526751

**Towards Resource Efficient Reactive and Proactive Auto Scaling for Microservice Architectures** — Ahmad et al., Journal of Systems and Software 2025. Реактивный и предиктивный HPA для ограниченного ресурса с учётом задержки запуска и остановки pod.
*Значение для работы:* полезна при выборе базового метода сравнения и сценариев нагрузки; рассматривает горизонтальное масштабирование.
https://doi.org/10.1016/j.jss.2025.112390

**GraphPilot** — Ho et al., UCC 2025. Автомасштабирование связанных сервисов с учётом временных зависимостей и повторных колебаний ресурса.
*Значение для работы:* колебания масштабирования рассматриваются как отдельная проблема. Подход с графовыми моделями и RL слишком сложен для базовой НИР.
https://doi.org/10.1145/3773274.3774260

## 5. Постановка эксперимента

| Параметр | Предлагаемое решение |
|---|---|
| Стенд | 3–5 микросервисов в Kubernetes; один повторяемый профиль нагрузки для всех режимов |
| Сравнение | статические лимиты CPU; базовый двухуровневый контроллер; при возможности — штатный HPA как отдельный ориентир |
| Нагрузка | плавный рост, ступень, короткий всплеск, волна; одинаковые входные профили |
| Метрики | P95/P99 задержки, доля запросов за SLO, лимиты и использование CPU, число переключений, время восстановления |
| Повторы | не менее 10 прогонов каждого сценария; медиана и разброс |
| Контроль | фиксировать версию Kubernetes, размер узлов, период метрик и параметры контроллера |

**Гипотеза.** При скачках нагрузки и задержке метрик контроллер может чаще менять CPU-лимиты и временно выходить за SLO. Это нужно проверить на стенде: эффект может не проявиться.

## 6. План НИР

1. Обзор литературы, выбор открытого кода и уточнение метрик устойчивости.
2. Стенд, генератор нагрузки, сбор метрик, воспроизводимые базовые прогоны.
3. Серии экспериментов при разных нагрузках и задержках обратной связи; графики и анализ ограничений.
